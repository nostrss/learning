헤더 레이아웃 (RFC 6455 §5.2)

바이트 0: FIN(1) RSV1-3(3) opcode(4)
바이트 1: MASK(1) Payload len(7)
이후:     [확장 길이 0/2/8B] [마스킹 키 0/4B] [페이로드]

예: 클라이언트가 "Hello" 전송 → 81 85 xx xx xx xx ?? ?? ?? ?? ?? (11B)
    서버가 "Hello" 전송     → 81 05 48 65 6c 6c 6f (7B, 마스킹 없음)

Payload 길이 인코딩

7비트 값실제 길이
0–125그 값 그대로
126다음 2바이트 (16비트 unsigned)
127다음 8바이트 (64비트 unsigned, 최상위 비트 0)

opcode 표

값이름분류메모
0x0Continuation데이터단편화 조각 (첫 조각 제외)
0x1Text데이터유효한 UTF-8 필수
0x2Binary데이터
0x3–0x7(예약)데이터
0x8Close컨트롤종료 핸드셰이크
0x9Ping컨트롤수신 시 Pong 의무
0xAPong컨트롤
0xB–0xF(예약)컨트롤

규칙 요약

마스킹클라→서버 MUST (TLS여도) · 서버→클라 MUST NOT. 위반 시 상대가 연결 종료
마스킹 알고리즘페이로드[i] XOR 키[i mod 4], 키는 프레임마다 무작위 4바이트 (§5.3)
마스킹의 목적암호화 아님 — 중간 프록시 캐시 오염 공격 차단 (§10.3)
컨트롤 프레임페이로드 ≤125B, 단편화 금지, 데이터 조각 사이 끼어들기 가능 (§5.5)
단편화첫 조각: FIN=0 + 실제 opcode → 중간: FIN=0 + 0x0 → 마지막: FIN=1 + 0x0 (§5.4)
브라우저 API단편화는 보이지 않음 — onmessage는 조립된 메시지 단위 (DevTools도 메시지 단위)
ping/pongPing 수신 시 Pong MUST (면제: Close를 이미 받은 경우). 페이로드는 메아리. 밀리면 최신 것만 응답 가능. 자발적 Pong = 단방향 하트비트 (§5.5.2–3)
브라우저와 pingJS에 ping API 없음 — 서버 ping엔 브라우저가 자동 pong. 클라이언트 생존 확인은 앱 수준 하트비트로 (서버는 socket.ping())
